# Reference — tripwires

> Hand-written. **Not** generated by `docs/reference/generate.py` — it is not in that script's
> `RENDERERS` and carries no `GENERATED_NOTE`. `tests/test_reference_docs.py` asserts every `.md` file
> under this directory is either rendered from source or explicitly declared hand-written in that
> test's own `HAND_WRITTEN_REFERENCE_FILES` set; this file is declared there. Update it by hand when a
> name, path, or literal it documents changes — nothing regenerates it for you.

A tripwire here is a literal name, path, or string that a second place in this repository depends on
without either place enforcing the dependency structurally. Renaming, moving, or rewording the first
place breaks the second **silently** — no import error, no exit code, just a doc that lies or a check
that stops checking. The **Test** column names what actually catches it today; `—` means nothing does
and the row is disclosure, not coverage.

| Tripwire | What breaks silently | Test |
|---|---|---|
| Renaming a doc file cited by name elsewhere (`03_architecture.md`, `06_adaptation_notes.md`, `07_troubleshooting.md`, …) | Every markdown link and prose mention pointing at the old name goes stale — a 404 nobody clicks, or text that now names a file that isn't there | `tests/test_tripwires.py::MarkdownLinkTests` |
| `bin/drive_map.py`'s `ROOT_FILES` / `FOLDERS` naming a run-folder file or directory | A renamed/moved file the schema still expects makes `DRIVE_MAP.md` drift from the real drive, or reports a real file as outside the schema forever | `tests/test_drive_map.py::test_added_and_removed_files_make_the_map_stale_by_name` |
| Skill directory name = the skill's own `name:` frontmatter = every prose reference to it (routing tables, other skills' prose, this hook's own setup-pointer line) | The skill becomes uninvokable by the name docs still tell an agent (or a person) to use; a routing table entry silently points at nothing | `probes/probe_gear_names.py` (the six gear skills + `hyperspace-setup`) and `tests/test_tripwires.py::SkillNameReferenceTests` (every other prose mention, including `hooks/session-start.sh`'s own text) |
| A skill's prose naming a `bin/<script>.py` it invokes (e.g. `.hyperspace/env/bin/python "${CLAUDE_PLUGIN_ROOT}/bin/loop_state.py"`) | The skill's own instructions break the first time an agent tries to run them — not at review time | `tests/test_tripwires.py::BinScriptReferenceTests` |
| `.claude-plugin/plugin.json`'s `name` + `.mcp.json`'s server key composing the `mcp__plugin_<name>_<server>__*` tool prefix Claude Code assigns a plugin-bundled MCP server | Every hardcoded copy of the prefix (`probes/probe_whole_path.py`'s `--allowedTools`, `docs/reference/mcp-tools.md`'s hand-typed prose in `generate.py`) goes stale; a headless run's tools are silently denied rather than erroring | `tests/test_tripwires.py::McpToolPrefixTests` |
| The `{plugin}--v<semver>` release-tag convention (`claude plugin tag`) and a dependent plugin's `allowCrossMarketplaceDependenciesOn` | Renaming the plugin without re-tagging leaves a dependent's semver range unable to resolve — it just can't find a satisfying version, with no error naming why | `—` (documented in `README.md` "Building on it"; no automated check in this repository) |
| `completed_by` closure labels `hyperspace-verifier` / `hyperspace-console`, quoted in `bin/node_gates.py` | Renaming either label makes a genuinely-closed row (verifier- or console-stamped) unrecognized by the Build gate's `--graph-snapshot` path — it refuses a row that was actually done | `tests/test_port.py::test_build_gate_accepts_the_plugins_closure_labels` |
| Refusal strings quoted verbatim in `docs/07_troubleshooting.md`, sourced from `bin/node_gates.py` constants (`_C10_REFUSAL`, `_WHOLE_PATH_REFUSAL`, `_PYDANTIC_MISSING`) and inline messages | The message wording drifts from the doc; an agent that hits the refusal and greps docs/07 for it won't find the row, or finds one describing a message that no longer exists | `tests/test_tripwires.py::Docs07RefusalTests` |
| `ui/SOURCE.md`'s pinned Caelos commit + `VITE_HUMAN_OWNER=user` in `ui/build.sh` | The two drift apart — a rebuilt console with a different owner default, or a commit bump nobody re-ran the build for | `probes/check_ui_build.py` (CI's console-reproducibility check) |
| The org's CI allowed-actions policy (github-owned actions + two additional allowed patterns) | Adding a third-party GitHub Action outside the two patterns fails CI at *startup*, before any step runs — reads as an opaque policy denial, not a code error | `—` (org-level GitHub policy; nothing in this repository enforces or documents the exact pattern set) |
| This hook's own primer markers, `<!-- acing-hyperspace:begin -->` / `<!-- acing-hyperspace:end -->` (`hooks/session-start.sh`) | A rename breaks the block-extraction every hook test relies on — the primer looks like it silently vanished from session preload, not like a string changed | `tests/test_hooks.py` (`_extract_delivered_block`) |
| Headless `claude -p` runs needing `--allowedTools` (no human to answer a permission prompt) | Every tool call is silently denied — a headless probe or script hangs or no-ops rather than erroring | `probes/probe_whole_path.py`'s own `--allowedTools` usage; `docs/06_adaptation_notes.md` §12 "Headless sessions" |
| `.hyperspace/config.toml`'s `worklog_owner` key — read only by `hooks/session-start.sh`; `hyperspace/config.py`'s `Config` dataclass has no field for it and is not expected to grow one. Its value names who owns the session preload and the agent-facing tool surface — **never the store**: when this engine is installed, the worklog store is always its own SQLite (`.hyperspace/graph.db`), regardless of this key's value (joint plan with a sibling plugin, 2026-09-27) | If `hyperspace/config.py` ever becomes a strict/unknown-key-rejecting reader instead of a selective `.get()`-based one, a config file carrying `worklog_owner` (hand-written or written by a future setup revision) could start failing to load for every *other* consumer, not just this hook. Separately, a reader that took this key to mean "the store lives elsewhere" would be wrong on its face | `tests/test_hooks.py::WorklogTests` |
| The `worklog` table's column names (`summary`, `author`, `created_at`) hardcoded in `hooks/session-start.sh`'s own SQL, sourced from `hyperspace/store/schema.sql` | A column rename in the schema doesn't error — the hook's `except Exception: rows = []` guard swallows it, so the worklog block just silently stops appearing forever | `tests/test_hooks.py::WorklogTests` (its fixture executes the real `schema.sql`, so a rename there fails the fixture, not just the hook) |
| `.hyperspace/config.toml`'s `worklog_mirror_dir` key (v0.1.2) — read only by `hyperspace/store/worklog_mirror.py`; `Config` has no field for it, same reason as `worklog_owner` above. Its value names where the derived markdown mirror is rendered, relative to the project root — and the mirror's own **file format** (frontmatter keys `date`/`author`/`summary`/`tags` plus this engine's `row_id`, JSON-scalar-encoded values, filename `<compact-timestamp>-<slug>-<row-id8>.md`) is itself a tripwire: a sibling plugin's own reader depends on that exact shape without either side enforcing the dependency structurally, since the two plugins never call into each other's code | Same class of silent config-load failure as `worklog_owner`. Separately, changing the frontmatter keys, their encoding, or the filename pattern breaks that sibling's reader at runtime on the other side of the process boundary — no import error on either side | `tests/test_worklog_cli.py::test_append_renders_mirror_file_with_exact_frontmatter` |
| `.hyperspace/config.toml`'s `worklog_default_project` key (v0.1.2) — read only by `hyperspace/worklog_cli.py`; `Config` has no field for it, same reason as `worklog_owner` above. Its value is the project code `hyperspace worklog append`/`import` fall back to when no project is stated (a sibling plugin has no project concept of its own) | Same class of silent config-load failure as `worklog_owner` | `tests/test_worklog_cli.py::test_append_default_project_from_config_key` |
| The `hyperspace worklog` CLI's JSON shapes and exit codes (`hyperspace/worklog_cli.py`) — a sibling plugin's adapter shells out to this contract and parses stdout, with no shared type or schema on either side of the process boundary | A field rename, a shape change, or an exit-code change breaks that adapter at runtime, not at review time, and neither side's test suite sees the other's | `tests/test_worklog_cli.py`; `CLI_CONTRACT.md` (pasted-from-real-runs reference for the sibling plugin's implementer) |

## Coupling to know before editing

- **`node_gates.py`'s message text is prose someone reads under stress** (mid-refusal, looking for the
  fix). `docs/07_troubleshooting.md` quotes it for exactly that moment. A message and its doc row can
  drift in *wording* (a trailing citation added, a clause reworded) without drifting in *meaning* —
  `Docs07RefusalTests` checks the longest placeholder-free excerpt is still present verbatim, not that
  the two strings are identical byte-for-byte start to end. See that test's docstring for why.
- **`docs/reference/*.md` is either fully generated or fully hand-written — never both.** A file that
  is 90% generated with one hand-edited paragraph will have that paragraph silently overwritten the
  next time someone runs `generate.py` with no warning, because the generator does not know the
  paragraph is there to protect.
- **The six gear skill directory names (`gear2-understand` … `gear6-live`) plus `acing-hyperspace` and
  `hyperspace-setup` are the plugin's entire skill surface.** `probes/probe_gear_names.py` enforces the
  set is a subset of the expected eight; it does not enforce that every *prose reference* to one of
  those names still resolves — that is this file's `SkillNameReferenceTests` row, added for exactly
  this plugin's own new file, `hooks/session-start.sh`, which names `hyperspace-setup` in a runtime
  message a human actually reads.
